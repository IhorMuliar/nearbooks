# NEAR Books deployment

The live contract is [`nearbooks.near`](https://nearblocks.io/address/nearbooks.near) on mainnet. `nearbooks-v6.okf-kill-1792497882.testnet` is the test and demo record: rejection paths, the re-pin timelock and all three prediction outcomes were exercised there.

`make readme` generates the marked tables from `contract/deployment.json` and `site/contract-cache.json` (mainnet; state read with `make cache`), and from `contract/deployment-testnet.json` and `site/contract-cache-testnet.json` (testnet). `make verify` fails on a stale table or on a hand-written hash that is not in the records. `make verify-deploy` and `make verify-deploy-testnet` check the records against the chain. Snapshot checks, owner powers, the timelock and earlier designs are in `docs/attestation.md`.

## Keeper

`keeper/keeper.py` (standard library only) runs daily from `.github/workflows/keeper.yml` at 00:20 UTC, or by hand ([run logs](https://github.com/IhorMuliar/nearbooks/actions/workflows/keeper.yml)):
1. It refuses to run unless its own key, read on chain, is a function-call key for this contract limited to `keeper_request_snapshot` and `resolve_prediction`.
2. For today and any earlier Pending resolve date without an attested snapshot, it finds the first mainnet block of the date and of 28 days earlier (binary search over RPC with backoff), checks the budget and daily cap, calls `keeper_request_snapshot(date, B, B28)` and waits for the attested result.
3. It calls `resolve_prediction` for every Pending prediction whose `resolve_after` now has an attested snapshot.

It logs JSON lines, and a second run on the same day does nothing. `--dry-run` (`make keeper-dry`) plans without a key; `--network testnet` targets testnet. It waits for each `send_tx` to land in a block, so a refused transaction fails the run at once.

It spends from the contract's prepaid budget (rules and leak bounds: `docs/attestation.md`, "Keeper budget"): 0.03 NEAR (`min_request_deposit()`) per request, at most 0.06 NEAR per UTC day, counted gross. The GitHub secret `NEARBOOKS_KEEPER_KEY` would hold only the function-call key; the full-access key never leaves the deployer's machine.

The key's gas allowance is 1 NEAR because a 300 Tgas call needs about 0.3 NEAR of balance and allowance up front at the pessimistic gas price; only burnt gas is charged (0.0013 NEAR for the first mainnet request). The first key (0.25 NEAR allowance, account 0.29996 NEAR) got the first run refused with `NotEnoughBalance` before anything was spent, so the account was topped up and the key replaced (transactions above).

The first mainnet snapshot cost the budget 0.02071 NEAR (0.01 NEAR to OutLayer plus storage), leaving 0.47929 NEAR. A request needs 0.03 NEAR available, so that covers 22 more daily snapshots. Tests: `contract/src/tests.rs`, section "keeper budget"; `tests/test_keeper.py` (RFC 8032 signing vectors, transaction encoding, first-block search, run logic).

## Predictions

Six dated, falsifiable claims from `pipeline/predictions.json`, with no stakes; the demo predictions were testnet-only. P4 used to be "break-even volume above 2x current volume", which needs off-chain volume data. It is now the same inequality measured on chain: break-even volume / current volume = new supply / NEAR captured.

P5 and P6 were added on 2026-10-21 so that two predictions are decided before judging: P5 on 2026-11-05, in the submission window, and P6 on 2026-11-15, the day before judging starts. Unlike the near-certain P1-P3, they were chosen to be uncertain. Our rough odds, from the 2026 history of 28-day windows rebuilt from `data/snapshot-2026-10-20`:

| Prediction | Our odds it is confirmed | Why |
|---|---|---|
| P1, P3 | above 95% | Supply has grown in every sampled interval of 2026, and nothing that would stop issuance takes effect before 2027 |
| P2 | about 90% | The buyback wallet only ever lost NEAR in a few small outflows (12,025 NEAR in all) |
| P4 | about 90% | The 28-day ratio stayed between 0.05 and 0.25 all year |
| P5 | about 60% | Net issuance has stayed between 87,100 and 88,600 NEAR a day since June and has eased about 1,000 a day over the last month |
| P6 | about 55% | 0.1727 is near the top of the year's range (mean 0.139); after high readings the ratio usually fell back, and revenue-wallet inflow is softening |

### Step 4: dashboard

A snapshot is verified only if its worker hash is in `contract/known_workers.json` and is the pin for that date, OutLayer's attestation matches its wasm, input and output hashes, and the attested transaction called this contract.
