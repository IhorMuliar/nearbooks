# NEAR Books deployment

The live deployment is the mainnet contract [`nearbooks.near`](https://nearblocks.io/address/nearbooks.near). The earlier testnet deployment (`nearbooks-v6.okf-kill-1792497882.testnet`) is kept as the test and demo record: it is where the rejection paths, the re-pin timelock and the three possible prediction outcomes were exercised.

The tables between `begin`/`end` markers are generated by `make readme` from `contract/deployment.json` and `site/contract-cache.json` (mainnet; the contract state last read with `make cache`), and from `contract/deployment-testnet.json` and `site/contract-cache-testnet.json` (testnet). `make verify` fails if any of them is stale, and it also fails if a hash written on this page by hand is not in the committed records. `make verify-deploy` compares `contract/deployment.json` with mainnet, `make verify-deploy-testnet` the testnet record with testnet.

## Keeper

`keeper/keeper.py` (standard library only) runs once per UTC day, from `.github/workflows/keeper.yml` at 00:20 UTC or by hand (every run's log: https://github.com/IhorMuliar/nearbooks/actions/workflows/keeper.yml):
1. It checks its own key on chain and refuses to run unless the key is a function-call key for this contract, limited to `keeper_request_snapshot` and `resolve_prediction`.
2. For today, and for any earlier resolve date of a Pending prediction, it skips dates that already have an attested snapshot. For each remaining date it finds the first mainnet block at or after 00:00 UTC of the date and of 28 days earlier (binary search over mainnet RPC with backoff). It checks the contract's budget and daily cap, calls `keeper_request_snapshot(date, B, B28)` and waits for the attested result.
3. It calls `resolve_prediction` for every Pending prediction whose `resolve_after` now has an attested snapshot.

It logs JSON lines. `--dry-run` (`make keeper-dry`) plans without a key and signs nothing. A second run on the same day does nothing. `--network testnet` runs it against the testnet deployment. It sends with `send_tx` and waits until the transaction is in a block, so a transaction the network refuses fails the run at once.

**Why its spending is bounded.** A NEAR function-call access key cannot attach a deposit (the protocol refuses it with `DepositWithFunctionCall`, shown on testnet). So the keeper cannot pay OutLayer itself. The contract holds a prepaid budget instead:
- anyone can fill it with `fund_keeper`,
- only the account the owner names with `set_keeper` may draw from it, through the non-payable `keeper_request_snapshot`,
- each request draws exactly `min_request_deposit()` (0.03 NEAR), and at most the daily cap per UTC day, counted gross. The cap is 0.06 NEAR and at most 1 NEAR by contract rule.

For these requests OutLayer's payer is the contract. The callback credits the unused storage reserve back to the budget instead of sending it to the keeper. OutLayer refunds the unused part of its 0.01 NEAR run deposit with a plain transfer, which the contract cannot attribute, so it lands in the contract's free balance and the budget ledger never overstates what is there.

The key's gas allowance is 1 NEAR. A 300 Tgas call needs about 0.3 NEAR of account balance and of allowance up front, at the pessimistic gas price; only the gas actually burnt is charged (the first mainnet snapshot request used 0.0013 NEAR). The first key had a 0.25 NEAR allowance and the account 0.29996 NEAR, so the network refused the first keeper run with `NotEnoughBalance` before anything was spent; the account was topped up and the key replaced (transactions above). The key's other limits were checked on testnet and refused before execution, at no cost: `ReceiverMismatch` for a call to another contract, `MethodNameMismatch` for any other method, `RequiresFullAccess` for a transfer.

The GitHub secret `NEARBOOKS_KEEPER_KEY` would hold only that key. The keeper account's full-access key never leaves the deployer's machine. In the worst case a leaked key spends the daily cap on snapshots for dates of the attacker's choosing, plus the remaining allowance as gas. It cannot move funds anywhere else.

The first mainnet snapshot cost the budget 0.02071 NEAR (0.01 NEAR to OutLayer plus its storage), leaving 0.47929 NEAR. A request needs 0.03 NEAR available, so that covers 22 more daily snapshots. Contract tests: `daily_cap_is_enforced_and_resets_the_next_utc_day`, `a_stranger_cannot_spend_the_keeper_budget`, `the_owner_cannot_spend_the_keeper_budget`, `unused_storage_reserve_returns_to_the_budget_not_to_the_keeper`, `rejected_keeper_run_returns_the_whole_reserve_to_the_budget`, `keeper_cannot_spend_more_than_the_budget`, `budget_accounting_fund_and_withdraw` and more in `contract/src/tests.rs`. Python tests in `tests/test_keeper.py` cover the RFC 8032 signing vectors, the transaction encoding, the first-block search and the run logic.

The contract-side rules (calls, events, accounting) are in `docs/attestation.md`, section "Keeper budget".

## Predictions

The claims are dated and falsifiable, and there are no stakes. All six come from `pipeline/predictions.json`. P4 used to be "break-even volume above 2x current volume", which needs off-chain volume data. It is now the same inequality measured on-chain: break-even volume / current volume = new supply / NEAR captured. The demo predictions were testnet-only.

P5 and P6 were added on 2026-10-21 so that two predictions are decided before judging (P5 on 2026-11-05, during the submission window; P6 on 2026-11-15, the day before judging starts). Unlike P1-P3, which are near-certain, they were chosen to be genuinely uncertain. Our rough odds, from the 2026 history of 28-day windows rebuilt from `data/snapshot-2026-10-20`:

| Prediction | Our odds it is confirmed | Why |
|---|---|---|
| P1, P3 | above 95% | Supply has grown in every sampled interval of 2026, and nothing that would stop issuance takes effect before 2027 |
| P2 | about 90% | The buyback wallet only ever lost NEAR in a few small outflows (12,025 NEAR in all) |
| P4 | about 90% | The 28-day ratio stayed between 0.05 and 0.25 all year |
| P5 | about 60% | Net issuance has stayed between 87,100 and 88,600 NEAR a day since June and has eased about 1,000 a day over the last month |
| P6 | about 55% | 0.1727 is near the top of the year's range (mean 0.139); after high readings the ratio usually fell back, and revenue-wallet inflow is softening |

### Step 4: dashboard

`make site` serves the page at http://127.0.0.1:8000/site/. It reads the snapshots, predictions and pin history from the mainnet contract in the browser. A snapshot is marked **verified** only if all of these hold:
- its worker hash is in `contract/known_workers.json`,
- that hash is the contract's pin for that date,
- OutLayer's attestation matches the snapshot's wasm, input and output hashes,
- the attested transaction called this contract.
